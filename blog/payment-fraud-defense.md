# BIN Finder без кардинга: как строить защитную проверку платежей

BIN (Bank Identification Number), также называемый частью IIN (Issuer Identification Number), — начальные цифры номера платёжной карты, которые могут указывать на платёжную систему и эмитента. Сам по себе BIN не подтверждает, что карта действительна, что ей владеет предъявитель или что транзакция безопасна.

Автоматизация проверки реальных карточных дампов, поиск «рабочих» карт и отбор карт для кардинга — это не та задача, для которой предназначен этот учебный проект. Вместо этого рассмотрим безопасный вариант: как система защиты может находить подозрительные платёжные события, используя минимальный набор сигналов и синтетические данные.

## Почему одной проверки недостаточно

Устойчивое антифрод-решение не опирается на одну характеристику карты. Оно комбинирует контекст транзакции, частоту попыток, историю учётной записи, результаты проверок адреса и защитного кода, правила процессинга и подтверждённые сигналы от платёжного провайдера. Ни один из этих сигналов по отдельности не является доказательством мошенничества.

## Учебная реализация

Папка `payment-fraud-defense/` содержит локальную демонстрацию на Python. Она:

1. читает только CSV, помеченный как синтетический;
2. отказывается обрабатывать поля с полными номерами карт, CVV/CVC, трековыми данными и BIN/IIN;
3. присваивает условный риск-балл по простым объяснимым правилам;
4. записывает только синтетический идентификатор события, балл и причины для ручной проверки;
5. не делает сетевых запросов и не принимает решения об авторизации платежа.

Запуск:

```bash
cd payment-fraud-defense
python3 main.py
```

## Как развивать защитную систему

- Использовать токенизированные идентификаторы транзакций вместо платёжных реквизитов.
- Подключать сигналы антифрод-платформы через утверждённые API платёжного провайдера.
- Измерять false-positive rate и проверять, не затрагивают ли правила непропорционально законных клиентов.
- Направлять спорные случаи на ручную проверку, а не автоматически отклонять платежи по одному правилу.
- Ограничивать доступ, сроки хранения и журналирование чувствительных данных.

## Вывод

Надёжная система — не инструмент, который обещает определить «рабочую карту» по первым цифрам. Это контролируемый процесс управления риском, минимизации данных и проверяемых решений. Тестируйте его на синтетических примерах и применяйте к реальным платежам только через одобренную инфраструктуру и в рамках требований безопасности.
